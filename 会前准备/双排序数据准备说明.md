# 双排序数据准备说明

这份说明给第一次接触程序的同学使用。双排序程序需要把每个候选放在同一个“目标 + 对接协议”下比较：一套是常规排序，另一套是在基础分上给低热度候选一点新颖度加分。这个加分只是帮助寻找值得核验的低报道候选，不是疗效分，也不能替代实验。

## 程序需要的记录

对同一个目标、同一个对接 protocol 的所有候选，都要准备下面三类数据。`source` 要能指向原始文件、数据库页面、检索记录或执行日志，不能只写“网络资料”。候选身份另需记录 `identity`；实际引擎接受 `verified` 或 `pending` 两种状态。

```json
{"status": "verified", "source": "..."}
```

只有 `identity.status = "verified"` 且有身份核验来源的候选才可入队列；`pending` 只能保留为待补数据。

### 1. 对接记录 `docking`

每条候选至少一条：

```json
{"score": -8.1, "source": "...", "protocol": "...", "target": "EGFR ..."}
```

`score` 是在统一协议下得到的对接分数，`protocol` 应写清靶点结构、软件和关键参数、受体/配体处理方式等，`target` 必须和全局元数据中的目标完全一致。不同目标或协议的分数不能直接混排；没有对接结果就留缺失，不能猜一个分数。

### 2. 风险过滤记录 `filter`

每个适用的过滤规则都要有记录：

```json
{"status": "pass", "source": "...", "policy": "filter-v1"}
```

`status` 只能是 `pass`、`fail` 或 `unknown`。`fail` 的候选不能进入排名；`unknown` 也不能当成通过，更不能当成零分。`policy` 必须等于全局元数据中的 `filterPolicy`。需要准备完整的风险过滤政策（例如哪些 ADMET、毒性或成药性规则属于硬过滤）、规则版本、运行日期和执行记录。

### 3. 热度记录 `heat`

每个候选要按统一检索口径记录：

```json
{"count": 12, "query": "...", "source": "...", "date": "2026-09-26"}
```

`count` 是检索命中数，必须同时保存完整检索式、数据库、同义词、疾病/靶点范围、查询日期和结果来源。所有候选应尽量使用同一日期和同一口径；不同口径的数量不能直接比较。已有一篇核验论文的 `pmid` 不是候选的总热度。

## 全局元数据

每次运行都要保存一份全局 `metadata`，例如：

```json
{
  "target": "EGFR ...",
  "protocol": "protocol-v1",
  "filterPolicy": "filter-v1",
  "heatDefinition": "统一检索式和数据库口径的命中数",
  "heatDate": "2026-09-26",
  "version": "..."
}
```

其中 `target`、`protocol`、过滤政策、热度定义、热度日期和数据版本必须与候选记录相互对应。若运行中途更换协议、过滤政策、检索式或数据版本，应建立新版本，不能把结果混在一起。

## 哪些候选能进入排名

待核对的化合物不进排名。只有在同一目标和同一对接协议下，过滤项全部为 `pass`，并且基础分 `base >= minBase` 的候选，才进入常规和冷门的共同队列。过滤项为 `unknown`、对接缺失、热度缺失或身份尚未核对时，应标注待补数据并排除，不能用零值填充来“凑齐”。

当前拟实施的计算参数如下。这些是待负责人确认的工程默认值，不是原方案已经证明的科学结论：

- `strong = -12`，`weak = -4`，`minBase = 50`。
- `base = clamp((weak - score) / (weak - strong) * 100)`，结果限制在 0 到 100。
- 热度分箱为 `0`、`1-9`、`10-99`、`100-999`、`>=1000`，对应 `novelty` 为 `1`、`0.75`、`0.5`、`0.25`、`0`。
- `cold = base + bonus * novelty`，默认 `bonus = 10`。

例如，统一协议下 `score = -8` 时，`base = 50`；若热度为 1 到 9，则 `novelty = 0.75`，冷门分为 `50 + 10 * 0.75 = 57.5`。这只能表示排序规则产生的分数，不能解释为结合力、疗效或临床获益。

`strong`、`weak`、`minBase`、热度分箱、`bonus`、过滤政策和权重都需要由负责人确认并写入版本记录。数据、阈值和权重不是原文件给定的科学结论，程序也不应把它们包装成已验证的药理规律。

## 本批 CSV 的现状

《肺癌EGFR教学候选_首批核验.csv》目前有 3 条教学样例：槲皮素、木犀草素、黄芩素。它们的身份、结构和各一篇示例文献已经整理，但 `docking_score`、`ob`、`dl`、`admet`、`literature_count` 等排序所需数据目前均为空；现有论文也不能直接当作统一热度计数。由此，当前真实 3 条都没有可用的对接、ADMET/过滤和热度记录，不能产出正式的常规排名或冷门排名，也不能把示例结果补写成正式结论。

## 会前需要补齐的工作

团队应先准备并确认：

1. 统一的 EGFR 目标定义和对接协议，完成同一协议下所有候选的对接并保存执行记录。
2. 完整的风险过滤政策、版本、输入数据和执行日志；每个候选逐项写 `pass`、`fail` 或 `unknown`。
3. 同日期、同检索式、同数据库范围的热度计数，并保留查询和来源记录。
4. 候选身份、结构、来源及去重结果，确保名称不会把黄芩素 Baicalein 与黄芩苷 Baicalin 混为一谈。
5. 由负责人确认上述排序规则、阈值和权重，再由程序按版本运行。

这是“准备统一数据并确认规则”的工作，不是先交一份文档审批再开始写程序。当前尚未完成完整多 Agent/扩容、第二案例或实验验证，后续沟通时不要承诺这些工作已经完成。


## 现在怎么使用

1. 打开本地网页的“双排序”，先看每个候选下面的“待补”项目。
2. 下载当前数据模板（文件夹里也有 `双排序待补数据.json`）。保留原始来源，填写统一协议、过滤记录和检索记录。未知继续留 `null` / `unknown`。
3. 点击“导入补齐的 JSON”。程序检查完后重算；格式错误不会覆盖原数据，缺记录的候选继续显示待补。
4. 比较两份排名及加分上限 0、5、10、20 的结果，导出计算记录供团队复核、报告引用。参数不是老师已批准的结论，无需先交这份说明才可使用程序。

对接分数须来自同一“越低越优”的评分方法；改变软件或打分单位，需要重新校准锚点。默认参数暂未验证。字段名与可直接导入的完整格式，以同目录 JSON 模板为准。

开发复核：网页导出的记录可运行 `node 本地服务/rank.cjs 输入.json 结果.json` 重算；程序使用相同引擎和原始精度。分数只在展示时保留两位小数，严格相等时并列名次（1、1、3），同分按 id 稳定显示。输出包含规则版本、全部输入、参数、排名与缺失原因。记录可以再次导回网页。
